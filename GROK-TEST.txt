Beeper Grok plugin 0.7.6 — shared-cloud onboarding acceptance

The plugin now has one default onboarding flow: inspect the shared cloud setup,
ask before a new installation, install official CLI/Server after consent, and
reuse the same profile from every device. Keep the user's current CLI, Server,
profile, accounts, and saved test messages unchanged during acceptance.

1. Extract this candidate to a new persistent /workspace directory outside the
   installed source and Beeper data. Verify SHA256SUMS, SOURCE-REVISION.txt and
   .grok-plugin/plugin.json. The manifest and helper must report 0.7.6.

2. Read the root and setup skills and changed helper code. Run isolated offline
   regressions from the extracted candidate directory:
   env -u BEEPER_PLUGIN_HOME -u BEEPER_READONLY python3 -m unittest discover -s tests -v
   Respect host resource limits. Fixtures simulate a fresh approved setup and
   do not download binaries or contact accounts. Report optional official-CLI
   skips and unavailable validators as such, not passes. VALIDATION.json records
   the author's test environment, not this host.

3. Reuse the established BEEPER_PLUGIN_HOME and this candidate's absolute HELPER.
   With BEEPER_READONLY=1 run only:
   python3 "$HELPER" onboard
   On the existing installation expect configured, approvalRequired false,
   reuseAcrossDevices true, readinessChecked false, and the same data directory
   and grok-bot target. This command only reads local installation files; it
   launches no process and does not contact the API or write consent. A configured
   result is not a claim that login or Server readiness was checked.

4. Run status once, then one messages list on the previously verified chat with
   limit 1. Confirm the same CLI/Server identity and account/profile. Keep bodies
   and credentials out of the report. Readiness initializing alone is not a
   reason to install, update, reconnect, or sign in again. Stop on unexpected
   identity/state instead of trying a different profile.

5. Return revision, exact test counts/skips, helper/manifest versions, onboard
   state, whether a consent file was created/changed (it must not be), and the
   bounded read result. Do not call setup, setup --approved, update, start,
   signin, recovery, account changes, sends, reactions, deletes, or cleanup.
   Do not destroy an existing installation to simulate the first-run case.

Once the user proceeds with activation, follow GROK-ACTIVATE.txt. Register all
five skills together through the supported Bot mechanism, and use this same
onboarding flow by default. The existing installation should be reused; it
should not ask to install software again. A fresh conversation on another device
must discover the saved skills and use the same cloud data directory. That check
is pending until actually performed. A native install-time callback has not been
verified; first-use onboarding does not prove that callback exists.

Prior evidence: 0.7.5 recognized the existing own reaction using the chat member
marked isSelf. This release retains that fix. Repeating its live send is not
needed. Live reaction removal/deletion, fresh-session report evaluation, native
skill registration, and real first-install UI behavior are separate acceptance
items; a passed synthetic suite is not full plugin acceptance.
